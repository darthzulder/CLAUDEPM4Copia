Web Service Smartsupervisión

Versión · Agosto 2025 Estilo · REST / JSON Transporte · HTTPS · TLS 1.2 Auth · JWT + HMAC-SHA256 Autor · Delegatura Consumidor Financiero — Dir. Tecnología

Recursos REST expuestos por la Superintendencia Financiera de Colombia (SFC) para que las entidades vigiladas mantengan al día la información de quejas o reclamos de los consumidores financieros. Sólo se admite REST + JSON: no se permite SOAP ni otras tecnologías. Los métodos HTTPS habilitados son GET, POST y PUT/PATCH.

URL Base https://<UrlBase>/api/ ⚡ Probar en Swagger UI

Definiciones

Conceptos base empleados a lo largo de esta especificación.

RESTEstilo de arquitectura cliente–servidor sobre HTTP; mensajes en JSON. JSONFormato ligero de intercambio de datos, legible por humanos y máquinas. JWTToken de acceso (RFC 7519) con header, payload y signature; propaga identidad y privilegios. HMACCódigo de autenticación de mensaje con función hash + llave secreta; verifica integridad y autenticidad. Recurso RESTElemento expuesto mediante una URI sobre HTTP para intercambiar representaciones de información. EndpointURL base + parámetros (obligatorios u opcionales) necesarios para ejecutar la operación. URL BaseDirección raíz para el consumo del REST.

Seguridad & firma de peticiones

Todas las comunicaciones viajan sobre TLS v1.2. El recurso debe exponerse exclusivamente a la SFC.

🔑 Firma X-SFC-Signature (obligatoria en toda petición)

Se firma con el algoritmo HMAC-SHA256 usando el secret asignado a cada entidad vigilada. El resultado viaja en la cabecera X-SFC-Signature.

GET Se firma la URL completa incluyendo los query params.
POST / PUT Se firma todo el cuerpo (JSON) convertido a cadena de texto.
Multipart La firma usa sólo codigo_queja + type; se omite file.

🎫 Tokens de sesión (JWT)

access tokenVigencia 30 minutos. Autoriza el consumo de recursos. refresh tokenVigencia 12 horas. Renueva el access token.

Vencidos ambos, la sesión expira y se debe volver a autenticar.

🛡️ Mecanismos de exposición admitidos

10.1 · TLSAutenticación mutua en doble vía mediante certificados SSL (handshake ClientHello / ServerHello). 10.2 · API KeyIdentificador único por cliente inyectado como header (ej. x-api-key). 10.3 · OAuthClientID + ClientSecret → token; refuerza el API Key con doble factor equivalente a JWT.

Puede usarse uno de los mecanismos, o combinar Autenticación (10.1) con API Key (10.2) u OAuth (10.3).

POST /api/storage/ Anexos de gestión: cierre y fraude · multipart/form-data ▶

Antes de gestionar, la entidad debe enviar los documentos anexos. Para cierre o fraude se exige una nomenclatura específica en el nombre del archivo.

Nomenclatura obligatoria en el nombre del archivo:
• Cierre → sufijo RESP_FINAL_SFC · ej. archivo_RESP_FINAL_SFC_1.docx
• Fraude → sufijo INV_FRAUDE_SFC · ej. archivo_INV_FRAUDE_SFC_1.docx
Reglas de cierre (estado_cod = 4)
estado_codDocumento RESP_FINAL_SFCResultado
= 4ExisteSe cierra la queja
= 4No existeNo se cierra la queja
≠ 4ExisteAlerta — no se permite la gestión
≠ 4No existeSe permite la gestión
Reglas de fraude (INV_FRAUDE_SFC)
  • Si un documento tiene los dos sufijos, se rechaza y debe enviarse por separado.
  • Si la queja tiene motivo de fraude, se permite la gestión; si no, se rechaza.
  • Si llegan cierre + investigación juntos, se valida primero la investigación y luego el cierre.
  • Si ya existía cierre previo, sólo se permite gestión de investigación por fraude.

estado_cod — gestión de cierre (Momento 3)

El valor 4 corresponde a la gestión de cierre. Debe acompañarse de un documento con el sufijo RESP_FINAL_SFC para que la queja se cierre efectivamente.

Los demás catálogos (canal, producto, motivo, tipo de persona, sexo, etc.) son suministrados por la SFC en anexos externos y no forman parte de este documento de construcción del web service.

Notas & condiciones

Notas generales
  • La entidad vigilada debe construir un desarrollo interno para el envío de la información.
  • El servicio expuesto por la SFC debe ser consumido por las entidades vigiladas y estará siempre activo.
  • Momento 2 → proforma F.0000-165 (formato 410) «Interposición de la queja o reclamo».
  • Momento 3 → proforma F.0000-166 (formato 411) «Gestión de la queja o reclamo».
  • Si un campo no aplica, se reporta vacío o con el valor por defecto que corresponda.
Desempeño

Disponibilidad superior al 99.7%, con réplica de información en distintos ambientes y redundancia en hardware y software (confiabilidad, integridad, disponibilidad y confidencialidad).

Condiciones para exponer el Web Service

Tras las pruebas de comunicación y conectividad en desarrollo y pruebas, la entidad remite a la SFC la dirección del Web Service productivo para configurar firewall/direccionamiento y registro. No se contempla el uso de VPNs.
